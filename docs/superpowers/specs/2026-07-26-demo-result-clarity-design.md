# SafeFix 演示结果可视化设计

## 问题

公开 WebUI 当前可以运行安全边界、验证反馈和一次性审批三个确定性场景，但三者最终都显示“演示成功”。失败、拦截、修正和授权复用拒绝只出现在时间线文字中，第一次使用者难以理解“中间失败为何仍算成功”，也不容易向课程评审者解释每个机制实际证明了什么。

## 方案比较

### 方案 A：结果简报卡 + 带状态的时间线（采用）

保留首页的一键演示。在结果页顶部增加场景结论卡，并为每个事件标注语义状态。

- 优点：不增加操作负担；直接利用现有确定性事件；最适合课堂演示和截图取证。
- 代价：需要为演示事件补充稳定的展示分类和场景结论元数据。

### 方案 B：逐步播放的演示向导

把事件按步骤逐个播放，由用户点击“下一步”查看。

- 优点：叙事感最强。
- 缺点：增加操作次数和客户端状态；不利于快速验收，不需要为本次作业引入。

### 方案 C：三个独立说明页面

每个机制提供固定图解，再链接到运行结果。

- 优点：说明空间充足。
- 缺点：固定说明与真实运行记录分离，容易变成静态宣传页，不能直接证明机制执行过。

## 采用设计

### 1. 结果简报

结果页在运行标题与审计时间线之间增加“机制验证结论”区域：

- 场景名称和一句话结论。
- 最终判定使用“机制验证通过”，避免误解为所有步骤都成功。
- 三个关键证据，以机器可验证的数据生成，不写死与实际事件脱节的结果。

各场景显示：

- 安全边界：危险命令已拒绝；命中安全规则；工具调用次数为零。
- 验证反馈：首次验证失败；错误补丁仍失败；正确补丁生成；最终验证通过。
- 一次性审批：进入人工检查点；篡改动作被拦截；原动作只批准一次；授权复用被拒绝。

### 2. 状态化时间线

每条演示事件增加状态徽标：

- `blocked`：已拦截，红色。
- `failed`：验证失败，橙色。
- `pending`：等待审批，黄色。
- `changed`：已修正，蓝色。
- `passed`：已通过，绿色。
- `info`：普通信息，灰色。

徽标必须同时包含中文文字，不能只靠颜色表达。技术详情继续折叠显示，并保留稳定机器码。

### 3. 数据与安全边界

- 展示分类和结论由服务端根据固定演示场景及稳定事件码生成。
- API 事件新增展示字段时保留原有 `code`、`summary` 和 payload，不改变审计语义。
- 未知事件使用 `info`，不猜测成败。
- 继续使用 Jinja 自动转义和客户端 `textContent`，禁止动态 HTML 注入。
- 公开演示仍只使用内置项目和 Mock，不接收项目路径、真实模型或 API Key。

### 4. 视觉方向

沿用现有深色工业控制台风格，不重做全站：

- 结论卡采用高对比边框和紧凑证据网格。
- 时间线状态通过左侧色条、中文徽标和机器码共同表达。
- 失败与拦截必须比最终绿色结论更先进入视线，清楚说明“系统通过正确处理失败而成功”。
- 760px 以下保持单列；键盘焦点、语义标题和对比度继续可用。
- 尊重 `prefers-reduced-motion`，不加入自动播放或强制动画。

## 测试与验收

### 自动化

- 三个公开场景的 API 返回稳定结论和事件展示状态。
- 反馈场景完整序列同时包含 `failed`、`changed` 和 `passed`。
- 安全边界包含 `blocked` 且工具调用为零。
- 审批场景包含 `pending`、`blocked` 和 `passed`。
- 结果页包含结论、关键证据、中文状态徽标和机器码。
- 恶意 payload 仍被转义；客户端不使用危险 DOM 插入 API。

### 浏览器

- 分别运行三个场景，不展开技术详情也能说明发生了什么。
- 反馈场景能直观看到“失败 → 失败 → 修正 → 通过”。
- 窄屏下结论证据不横向溢出。
- 页面无控制台错误。

## 不在本次范围

- 不增加真实模型调用。
- 不增加逐步播放、暂停或重放控制。
- 不修改核心策略、审批状态机或工具执行逻辑。
- 不引入前端框架或外部资源。
